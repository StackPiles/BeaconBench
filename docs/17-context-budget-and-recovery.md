# 長い会話の出力枠と、受入済み応答の復旧

## 入力と出力で同じ容量を使う

コンテキスト256K、最大出力128Kは、入力が常に128K以下という意味ではない。検索結果や対話履歴が増えた後も `max_tokens=131072` を固定すると、入力と予約する出力の合計が262144を超え、vLLMが生成前にHTTP 400で拒否する。

出力128Kを**上限**として保持し、必要な要求だけ残り容量へ合わせる方針を明示的に選べる。履歴・検索結果・思考を削ったり、温度・seedを変えたりしない。APIへ実際に送った出力枠は各要求の `request.json` と `context-budget.json` に保存する。

```
effective_output_cap = min(configured_output_cap, context_tokens - prompt_tokens_upper_bound)
```

入力だけで容量に達していれば、履歴を切り捨てず停止する。この方針はベンチマーク固有の操作回数・対話回数上限や、フレームワーク共通の累積出力上限を追加するものではない。

## Qwen/vLLMで確認した計数方針

モデル登録の `engine.context_policy` へ次の値を指定する。既存モデルの登録と過去planを変更せず、新しい接続プロファイルを作る。

| 値 | 対応する接続 |
|---|---|
| `qwen-vllm-context-fit-v1` | vLLMの `/tokenize` へ直接接続 |
| `llama-swap-qwen-vllm-context-fit-v1` | llama-swapの `/upstream/<model_id>/tokenize` 経由 |

vLLMのTokenizeChatRequestでは、非標準の `reasoning_content` がChat APIと同じように数えられない場合がある。確認したQwenテンプレートでは、計数要求だけに思考を明示的な本文表現として保持し、マーカー分の余裕を含む上界を使う。**生成へ送るmessagesは変更しない。** 推論APIが返した実際のprompt usageが上界を超えれば、計数の不成立として停止する。

この初版は対象Qwenの保存済み実要求158件で検証した。上界が実測を下回る要求はなく、既に受理・完了していた要求の出力枠も変わらなかった。別のテンプレート・モデルへの一般的な正確性を保証するものではない。未受入の他モデルへ自動適用しない。

計数の準備時間は `context-budget.json` へ別途記録する。TTFTと生成要求の時間は、その後の実際のChat API要求から測る。nativeの課題全体の時間には準備も含まれる。

## 原本を変えずに復旧する

失敗したrunのplan、回答、途中の要求・応答は保存する。修正したcontrollerや接続プロファイルを使う場合は、新しいplan/runと互換性の検証記録を作る。

- 完成済みの回答は、問題・seed・重み・サンプリング・helper・native環境を照合し、修正がその要求の出力枠を変えないことを確認して引き継ぐ。元のgeneration指紋と新しい指紋の両方を残す。
- nativeの途中再開では、受理・完了済み要求の原本をSHAで固定する。現在の要求が完全一致した場合だけ保存済み応答を再生する。一致しなければ、品質を理由とした再生成をせず停止する。
- 元のraw記録を複製する場合も `reused_from` を残す。論理的な課題のトークン量には元の実測を使い、今回新しく発生した消費には再生分を重複計上しない。
- native全体の元の開始・終了境界を復元できなければ、その課題の完了時間は不明とする。再開区間だけの秒数を課題全体の時間と表示しない。

生成前に拒否されたHTTP要求は、接続切断やモデルの不正解と区別する。任意のproviderエラー本文には認証値が含まれる可能性があるため、公開ログへコピーしない。本文のdigestと厳密に取り出したコンテキストの数値だけを `http-error.json` へ残す。

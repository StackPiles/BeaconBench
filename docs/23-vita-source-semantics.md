# Vita：公式の意味・合算予算・停止理由

2026-10-30。終了検査の原回答・原判定を保持し、固定された公式データの意味に沿った別版`vita-source-termination-v2`を実装する。新しい本評価を自動開始せず、最初に保存済み回答で検証する。

## 公式データを使う範囲

基準は[固定版の公式コード](https://github.com/QwenLM/BabelArena/tree/36960fbb7ee1aac5082fa7307264abc612a180f4/benchmarks/vitabench)と[固定版の公式データ](https://huggingface.co/datasets/Qwen/BabelArena/tree/e8f095bcd3c1a0e01cfa7d7fad526bf448e09823/vitabench)。問題本文、native採点条件、参照注文と商品を読み取り専用の個別資産として固定する。第三者データと個別環境のパスはリポジトリへ配布しない。

`vita_source_context`は抽出資産のpath・SHAと原問題のSHAを持つ。資産には元のtask、配布元・固定revision・原ファイルのSHA、点検済みの予算範囲を入れる。予算範囲は元指示の完全一致する条件文、公式rubricの文、対象注文系列、原文にある人数で固定する。現在の指示と異なる問題や、SHAが変わった資産を受け付けない。

公式の参照情報は判定役だけが使う。対象モデルと模擬顧客に参照注文・商品区分・採点基準を渡さない。顧客の確認文もv1から変えない。公式例にない手順や商品でも元の条件を満たせば認め、特定の商品ID・対象モデル名に対する例外を実装しない。

## 夕食などの商品意味

参照例で要望を満たすものとして使われている商品は、その例とrubricを合わせて意味を判断する。例えば、夕食条件のある公式例が食事を含むセットを使う場合、商品名に夕食という文字がないことだけで不足と判定しない。一方、実際の注文なし、違う商品、必要数不足は別に検査する。実世界の一般論で公式の参照例を置き換えない。

## 宿泊などを含む予算

`cost_ledger`はnativeの実注文・支払い応答から構築する。対象モデルや顧客が説明した合計金額を集計の入力にしない。店舗・宿泊・配送を区別し、公式rubricで固定した系列を全部集計する。別枠の費用を混ぜたり、宿泊を除いたりできない。

判定の`budget_checks`は、台帳にある対象注文IDの全体・人数・合計・1人あたり金額と一致する必要がある。例えば4人のセット240と宿泊160なら合計400、1人100。追加活動120があれば合計520、1人130である。宿泊を除いた単価で元の予算を満たす判定は受け付けない。

この計算は金額と対象範囲の検証であり、「前後」の合格幅を新しく定めない。定性的な充足は公式rubricと参照例を踏まえて判定する。未対応の取消・返金・変更を見つけた場合は不明として扱い、古い合計で充足にしない。

候補が終了不可・不明の場合も、同じ原文・全文・台帳を使う独立した確認を行う。確認できない場合は要確認を保持する。モデルの失敗、顧客役の逸脱、参照データの曖昧さを同一の点数へまとめない。

## 保存回答の点検

明示的な`termination-review RUN CONFIG`だけで開始する。較正済みの判定役を必要とし、資源予約を取得してSparkなどの指定APIへ判定要求を送る。対象モデルの生成、native対話の再開、公式採点、推論サービスの設定変更は行わない。

終了検査のinput・原判定・元statusのSHAを固定し、別の`termination-reviews/RUN/REVISION/`へ入力、実要求、応答、根拠、結果を保存する。失敗したnative対話も点検できる。点検を公式得点や新しい対話の成績として扱わない。CLIのCONFIGは個別の`source_context`と、model_id・preset・instrumentを持つhelperを指定する。

## 停止の表示と原本

新しいworkerは顧客終了検査による停止を`instrument_review_required`へ分ける。通信・起動などの基盤障害は従来の`infrastructure_error`のまま扱う。

旧runのstatusが`infrastructure_error`でも、保存イベントの`InvalidCustomerTermination`を確認できるときは、読み取り専用の`display_phase`と`stop_reason`で「終了判定の確認が必要」と表示する。元statusは変更しない。統合表示は計測用runの詳細理由を引き継ぐ。

同じ試行を引き直す再開ボタンは表示せず、サーバー側も再開を拒否する。保存回答の点検が完了した場合は、その新しい判定と費用を原判定とは別に表示する。成功になるまでの再生成、顧客の終了記号の削除、対象モデルへの不足項目の通知は行わない。

## 検証範囲

独自の正負controlは、参照例に沿う食事付きセット、宿泊を含む予算超過、異なる商品ID、注文漏れを含む。実モデルによるcontrolの受入と、保存済みの実対話の回帰検証を分けて記録する。これらは固定例での確認であり、母集団全体の判定精度を意味しない。

v1の終了検査、補助検査v2、旧runの凍結runtime・原回答・原判定は保持する。新しい顧客条件・終了検査を本評価へ適用する場合は、別版の資産・補助役の受入と明示的な実行指示が必要。

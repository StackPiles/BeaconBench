# 10 画面とモデル・設定切替

## 目的と現在の範囲

モデルや設定を切り替えるたびに実行スクリプトを編集せず、登録済みのモデルと設定を画面で選び、同じ課題で比較できるようにする。品質・消費・時間の違いから、個々の回答・操作・採点根拠まで調べられる画面を作る。

[画面試作](../ui/prototype/index.html)は、この操作と表示の設計確認用。選択・プリセット編集・実行計画の表示・ケース明細はブラウザー内で操作できる。結果例は架空で、接続・保存・モデル起動・ベンチマークは実行しない。

[実画面](../ui/runtime/index.html)は `beaconbench serve` から配信し、同じresolver・workerをCLIと共有する。登録済みモデルの接続確認、設定の保存・複製、計画確認、実行、停止・再開、定期 / 手動更新、実回答・思考・採点根拠の表示まで実装した。HTML単体では動かない。モデルの起動設定変更・統計区間・公開exportは未実装で、予定機能を操作可能に見せない。

## 保存済みケースの読み取り画面

実画面の「回答と根拠」は、問題内容・回答内容・採点根拠を同じ画面に表示する。広い画面では問題と回答の隣に採点根拠を置き、狭い画面では同じ順で縦に並べる。問題・回答は省略せず、長い本文やコードは領域内でスクロールする。Markdownの段落・見出し・表・コードをDOMのテキストとして整形し、モデル出力のHTMLやスクリプトは実行しない。

入力は保存された最初の対象モデルへの要求から取得する。共通の指示は問題の開閉欄に残す。会話課題は対象モデルと相手役の発言を時系列で表示し、メール草案などの保存操作の内容も回答に含める。native adapterが最終回答ファイルに採点結果JSONを書いた場合、そのJSONをモデルの回答として扱わず、保存された対象モデルの発言や提出操作から本文を表示する。原本は変更しない。

採点根拠は分野固有の単位とルールを保持し、テスト成否、制約別の照合、評価コメントを表示する。多数のチェックは不適合・不明を先に示し、適合項目も開いて確認できる。連続点へ合格閾値を追加せず、実行の成功と課題の達成、部分点と主指標を区別する。記録のない正解集合・理由・値を推測で補わない。採点器が抜粋だけを保存した基準には抜粋と表示する。

思考、実要求・操作・計測、採点原本、回答の保存原本は「詳細情報」に置く。通常の閲覧では思考や繰り返された要求本文を取得せず、開いたときに要求単位で取得する。採点補助役の記録も役割を区別する。表示を開いても生成・採点・run条件の更新は行わない。

## 設定を分ける単位

| 単位 | 内容 | 管理方法 |
|---|---|---|
| モデル接続 | 表示名、model ID、endpoint参照、認証の環境変数名、能力 | 個別環境のregistry。鍵の値は画面や公開設定に返さない |
| モデル資産 | 重みrevision、量子化、tokenizer、template | 版とhashを持つモデルの識別情報 |
| エンジン設定 | エンジンbuild、KV、MTP、graph、cache、並列度 | backend別のtyped preset。起動管理はhost adapterへ限定 |
| 生成設定 | 温度、top-p、思考、有効なpenalty、contextと一要求出力 | 名前付きpresetとして複製・編集・版管理 |
| 比較プロトコル | 問題、言語pack、採点器、helper、終了規則 | 変更を明示した固定protocol |
| 実行設定 | 各ケースの試行回数（既定1）、基底seed、集計方針 | セット・モデル・生成presetから独立し、同じ比較内で共有 |
| 実行計画 | 選んだ組み合わせと解決済みの全条件 | immutable snapshot。編集後のpresetから独立 |

設定名を変えただけで同じ条件の回答が再利用不能にならないよう、有効値からfingerprintを作る。内容を変えた同名presetは別revisionとする。古いrunは当時の実要求と設定を表示し、現在のpresetで上書きしない。

## 操作の流れ

1. **評価セットを選ぶ**：Quick / Detailedのケース集合と言語。
2. **試行回数を指定する**：各ケースの既定1回。任意の正の整数を入力し、セット切替でも保持する。
3. **モデルを選ぶ**：接続済み・未確認・非対応を区別し、複数選べる。
4. **生成設定を選ぶ**：基準presetの選択、複製、温度や思考・engine固有設定の編集。
5. **差分を見る**：基準から変わる値と、モデル間で対応しない設定を表示。
6. **計画を確認する**：構成・ケース・回数、上限、未検証の条件、資源配置を確認。
7. **実行する**：受入済みplanだけを明示的に開始。進捗・中断・再開を同じ画面で扱う。

初期の参照容量は256K / 一要求128K。独自の累積出力・操作回数制限は追加しない。画面では「追加制限なし」と「engineの容量」「公式タスクの期限」を分けて表示する。非対応モデルに黙って小さな値を送らない。

既存endpointへ接続するモードを基本とする。起動・停止も管理するモードはoperatorが設定したhost adapterと所有leaseを必要とする。画面へ任意のshell文字列を入力して起動する仕組みにしない。

## 比較の種類

| 種類 | 固定するもの | 変えるもの |
|---|---|---|
| モデル比較 | 問題・preset・helper・採点 | モデル構成 |
| 設定比較 | 問題・モデル・helper・採点 | 温度・思考・MTP等、選んだ設定 |
| 組み合わせ比較 | 問題・helper・採点 | モデル×presetの組み合わせ |

画面は `モデル数 × preset数 × ケース数 × 試行数` を表示する。これは試行数でありAPI呼び出し数ではない。対話型caseのAPI回数と累積token数は実行前には確定しない。予測値を出す場合は出典・不確実性を表示する。

意図した条件差を記録して比較できることと、条件が一致していることを区別する。結果には差分を残し、温度等が違うrunへ「同条件」の表示をつけない。

## 画面構成

### 比較結果

上部でrun、suite、言語、モデル、preset、採点版を選ぶ。正誤式の成功数、最適化の連続点、入力＋出力消費、課題時間を並べる。異なる品質の単位を一つの総合点へまとめない。

分野別の棒グラフ、モデルごとの消費・時間、品質と完了時間の散布図を候補にする。図にはサンプル数・単位・不明・打切りを示し、色だけで成功と失敗を伝えない。対象モデルとhelperの消費は表示を分ける。

### 比較の作成

モデルとpresetをチェックし、共通の条件を編集する。標準項目とbackend固有項目を分け、非対応・有効値不明を表示。選択と差分からresolved planを作る。

各ケースの試行回数は別の数値欄（既定1）で指定し、1 / 3 / 5回の補助ボタンも置く。0・負数・小数・空欄では計画確認を止め、該当欄に理由を示す。5回を上限としない。モデル変更・セット切替・preset複製で回数をリセットしない。

予定試行数は構成数・ケース数・回数をラベル付きで表示する。JSON等の詳細は折りたたみ、通常の計画確認ではモデル・エンジン・生成設定・容量・回数を表で示す。編集中の設定から保存済み結果を再計算しない。

### 進捗

現在のモデル・設定・case・段階、完了 / 予定 / 採点済みの件数、経過時間、出力増加、直近の更新時刻を表示する。生成完了と採点完了を分ける。

既定は小さいsnapshotの定期取得とし、手動更新も常に置く。通信途絶は停止と断定せず「更新が途絶えている」と表示する。保存回答全文をpollのたびに取得しない。表示hostは重い推論・採点を担当しない。

### ケース明細

問題の原文・日本語版、最終回答全文、tool時系列、原判定、根拠、終了理由、tokenと時間をtabで表示。公開可否と測定値の由来も示す。詳細はcase単位で遅延取得し、大きなrunでも画面の初期表示を軽くする。

### モデル・preset管理

モデルを登録し、接続情報・能力確認の状態を表示する。既存presetを複製し、新しい版として保存できるようにする。削除しても過去runのsnapshotは失わない。画面から環境変数の秘密値を読み出す機能は置かない。

## UIと実行基盤の境界

APIとCLIは同じregistry、schema、resolverを使う。画面の値はserver側で再検証し、古い画面が有効条件を上書きしないようversionまたはexpected fingerprintを照合する。

予定APIの役割：`models / presets`の取得と版付き保存、`plans`の解決と事前確認、`runs`の開始・状態・中断・再開、`comparisons`の集計、`cases`の必要な詳細取得。具体的なframeworkとversionは実装時にlockする。

初期の提供先はローカルhostとし、UI配布物は静的assetにする。認証・model keyはPython側の設定から解決する。外部公開・複数利用者・遠隔操作を追加する場合は、認証と操作権限を持つ別のdeployment profileにする。

## 受入条件

- 同じ選択からUIとCLIが同一のresolved planを作る。
- preset変更で過去のrunの条件が変わらない。
- 不明な能力・非対応設定・native上限を隠さない。
- 試行数をAPI回数や完了件数と取り違えない。
- 両セットで既定1回。切替でも入力回数を保持し、同じ値をresolved planへ保存する。
- 実測、架空例、未測定を画面上で区別する。
- token内訳を二重加算せず、成功率と最適化点を合算しない。
- キーボードで選択・dialog・詳細確認ができ、狭い画面でも内容が読める。
- 架空の結果例から、回答と採点根拠まで少ない操作で到達できる。

## 見た目と読みやすさ

- 操作に寄与しない装飾、重複見出し・試作警告・更新ボタンを置かない。試作状態は共通の一箇所で明示する。
- 本文・入力・表は14px以上、補足は原則12px以上。通常文字のcontrastは4.5:1以上を設計目標にする。
- 画面幅で余白と列数を変え、ページ全体の横はみ出しを作らない。横長の表は名前付きscroll領域に閉じ込める。
- 狭い画面でも主要navigationの文字を残す。選択・成功・失敗を色だけに頼らず表示する。
- キーボードfocus、dialog名、入力名、エラーとの対応、ライブ通知を持つ。Escでdialogを閉じ、元の操作へ戻る。
- 空状態、入力エラー、長い設定名、多数のpreset、長い回答も確認する。数値は単位・分母・対象を省略しない。

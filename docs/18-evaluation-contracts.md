## Vita：顧客役の逸脱をモデルの失敗へ混ぜない

保存されたQuick20では、顧客役への実際の要求に日本語の要望と公式の固定条件がすでに含まれていた。欠落した入力を補う修正ではない。

新しい生成版では、同じ固定指示の保持を顧客役だけに再確認する文を付け、顧客役の推論を有効にする。これは公式規則に基づく確認文を加えた派生条件であり、公式プロンプトの完全再現とは区別する。問題・条件分岐・終了規則は変えず、対象モデルへ顧客の非公開要望や採点条件を追加しない。顧客役は確認文を含む条件で別に受入する。生成後は保存された顧客システム指示と会話を検査し、逸脱または判定不能ならnative得点を残した参考値とし、能力比較から留保する。エージェントの誤答・拒否・ツール失敗だけを顧客役の逸脱にしない。

旧会話を点検しても新しい顧客条件の回答にはならない。新条件の能力を測るにはVitaの対話を再生成する必要がある。確認文の効果は少数の確認問題での受入であり、全会話での忠実さを保証しない。

## CRM：公式の0点と参照答えへの疑義を併記

Quick20の2件は抽出処理が正しくても、参照にない追加指摘があるためnative不一致となった。固定したデータ・規則・保存済み状態を照合し、参照答えに疑義が残る場合は、出典のrecord SHA、理由、証拠、公式URLを別の点検情報として固定する。

疑義のある課題は能力比較から留保し、公式の参照答え、抽出結果、0点を保持する。これを「正解へ修正した」とは表示しない。上流での確定や事前に定義した別評価版なしに部分点・代替の正解を追加しない。共有CRM環境の時点・状態の検証も従来どおり必要。

## 営業：取引前進と仕様への忠実さを分ける

日本語版の顧客意向判定は、全対話を受け取り最終的な顧客意向を判断する独自のLLM測定器であり、公式の英語・中国語BERT分類器・そのトークナイザーによる末尾128トークンとは異なる。この入力範囲と分類器の差を残し、表示は引き続き「日本語派生版」とする。公式BERTの日本語妥当性が未検証のため、公式128トークン条件を再現したとは呼ばない。

評価条件v2は `proportion=0.6` とプロファイル名を明示する。旧0.5の計算と結果は残す。保存された会話品質・意向判定が同じなら重みだけを変えて再集計できるが、その点差は能力改善を意味しない。日本語版の意向判定の入力範囲と測定器は変更しない。

商品仕様、適用範囲、保証、利用できる手段との一致を別の指示遵守検査として表示する。購入に至っただけで仕様違反を相殺しない。逆に購入に至らないだけで仕様違反とはしない。外部照会を実行したという主張と、顧客が販売窓口で確認する方法の提案を区別する。営業担当に実際に渡した固定指示だけを参照し、対象モデルへ渡していない禁止事項を後から追加しない。架空商談での将来のフォローアップ提案を、送信ツールがないことだけで違反としない。これは追加の監査であり、公式主得点へ独自の減点を混ぜない。対象モデル自身の仕様違反が見つかった課題は比較から除外しない。補助検査の自動判定は違反候補として表示し、主得点とは区別する。引用が原文に存在することは意味の正しさを保証しないため、候補の採否は前後の会話と指示を全文で点検する。

## 検査器の受入と原本

`fixtures/evaluation-contract-controls.json` は実際のベンチマーク回答と独立した架空の確認問題。顧客検査10件、営業検査8件で、整合・違反・不明を含める。違反判定には固定指示と対象の発言の完全一致引用を必須とし、発言者・番号も機械検証する。長い会話での数え間違いを避けるため、入力する各発言に0始まりの番号を明示する。規則の引用元はreferenceだけに限定し、検査役への説明文からの引用は受け入れない。不正な引用や判定形式は不明として残し、対象モデルの失敗に置き換えない。

固定したモデル・設定・検査方針のSHAに対し、入力が揃った整合・違反の全確認問題の一致と重要な誤判定0件を受入条件にする。固定指示または会話の欠落はモデルへ推測させず、前処理で不明にする。これは小規模な開発用受入であり母集団の判定精度ではない。受入に不合格となった判定も保存し、同じ条件の出力を引き直して合格扱いにしない。検査仕様を変えるときは理由と新しい指紋で再検証する。

2026-10-29の最終受入は、入力の揃ったVita検査9/9、営業検査7/7と、入力不足をモデル呼出しなしで不明にする2件の確認からなる。最初の営業検査は確認方法の提案を誤って違反とし、Vita検査にも訂正表現への過剰な判定があったため、一般的な仕様の区別を明確にし、2件の架空の訂正表現を追加した。入力不足を自然言語で伝えて判断させる検査にも誤判定が出たため、欠落を明示した構造化入力と決定的な前処理へ移した。同じ条件の16件のLLM応答は再利用し、不合格となった記録も保持している。この18件を未使用の評価集合や母集団精度とは扱わない。

Vita顧客役は、部屋条件・曜日分岐・既知の配送先・技術的失敗による許容終了の4つの独立した継続問題で4/4を確認した。推論なしの旧候補には曖昧な返答が残ったため不採用とし、同じモデルの推論あり・一要求16Kの別プリセットを受入した。native採点器も、変更した採点条件の正負controlを再受入する。

## 保存回答だけを点検する

新しい受入済みpackを別IDで登録し、明示コマンドで完了済みの保存回答を点検する。対象モデルの生成・試験の再開は行わない。

```sh
uv run beaconbench evaluation-review RUN_ID local/review-config.json
```

設定は `{"suite_id":"NEW_ACCEPTED_SUITE_ID","name":"評価条件v2・保存回答の点検"}`。同じ問題ID・出典・保存回答と元採点のSHAを照合し、新しい `evaluation-reviews` に別記録を作る。元回答、元採点、元runのsummaryは書き換えない。

結果画面の「採点版」で元の採点と新しい点検を切り替える。留保数、理由、引用、重み変更前の得点を明細に表示する。保存済みの旧生成条件を点検したことも明示する。新条件での本評価は別途明示的に開始する。

中継側は管理・保存・表示を担い、実モデルの顧客役・判定役とnative採点処理は計算ホストで実行する。対象モデルの設定、推論サービス、過去の固定runtimeはこの変更では更新しない。
